## 四、配置、安全与工程健康

### 4.1 【高】API Key 会被打进构建产物

`vite.config.ts`：

```ts
define: {
  'process.env.API_KEY': JSON.stringify(env.GEMINI_API_KEY),
  'process.env.GEMINI_API_KEY': JSON.stringify(env.GEMINI_API_KEY)
}
```

`define` 是**构建期文本替换**——只要 `.env.local` 里 `GEMINI_API_KEY` 有值，这个值就会以明文形式出现在 `dist/assets/index-*.js` 里，任何人解包 dmg 都能拿到。而 PicMan 现在是纯离线工具，压根不需要任何云端 key。

处置建议（需你确认）：删除 `define` 两个字段 → 删除 `.env.local` 中的该 key → 如果构建产物里出现过，还应视为已泄露并吊销。

### 4.2 【中】`index.html` 挂着 esm.sh 的 CDN importmap

```html
<script type="importmap">
  { "imports": { "react": "https://esm.sh/react@^19.2.4", ... } }
</script>
```

这是"在浏览器里直接跑 TSX，让 esm.sh 现场编译"的旧方案残留。它有三个问题：

1. 与"离线可用"原则冲突——断网即挂。
2. 是 `tauri.conf.json` 的 CSP 里必须放 `esm.sh` 的原因（安全面扩大）。
3. 容易误导：让人以为 `dist/` 之外还有一条能跑的路径。

实际构建走的是 Vite 打包，这段 importmap 对产线无任何作用。

### 4.3 【中】`package-lock.json` 被 gitignore

`.gitignore` 把 `package-lock.json` 排除了，导致依赖没有锁定版本，换台机器 `npm install` 可能装出不同版本，构建结果不可复现。应用类项目应当入库。

### 4.4 【低】其他

- `tauri.conf.json` 的 CSP 仍放行 `cdn.tailwindcss.com`（早已迁到 Vite 插件，无用）。
- `fs.all: true` + `$HOME/**` 的范围偏大，未来可收窄到具体目录。
- `releases/` 里的 dmg 与 `src-tauri/target` 下的产物重复，留一份即可。

### 4.5 【高】测试套件跑不完

`npx vitest run` **无法跑完**，卡在 `src/utils/__tests__/thumbnailGenerator.test.ts`——该文件在 jsdom 环境下调用 Canvas 2D，等一个永远不 settle 的 Promise，进程挂住不退出。我实测跑了 5 分 51 秒仍无任何输出，只能强杀。

分批实测结果：

| 文件 | 结果 |
|------|------|
| `utils.test.ts` | 15 passed |
| `taskScheduler.test.ts` | 31 passed |
| `lruCache.test.ts` | 30 passed |
| `blobManager.test.ts` | 18 passed |
| `hooks/__tests__/*`（3 个） | 62 passed |
| `thumbnailGenerator.test.ts` | **挂死** |

单跑这些能跑的是 156 个，与 `CLAUDE.md` 记录的"156 tests passing"吻合——说明历史上这个文件就没被纳入统计，但它一直在把你的完整测试命令拖死。

更讽刺的是：`thumbnailGenerator.ts` 这个模块本身**在主流程里零引用**，只有它自己的测试和性能基准在用它。也就是"一个没人用的模块，配了一个会把测试卡死的测试"。

处置建议：P1 做缩略图接入时，顺手把这个测试改造成真能跑的断言；在此之前，日常验证用
`npx vitest run src/utils/__tests__/{utils,taskScheduler,lruCache,blobManager}.test.ts src/hooks/__tests__`

### 4.6 【中】`tsc --noEmit` 有 8 处真实类型错误

`package.json` 里没有 `typecheck` 脚本，`npm run build` 走 esbuild 不做类型检查，所以这些问题一直没人发现。给 `tsconfig.json` 加上 `exclude`（原来连 `src-tauri/target` 的 2GB 生成物都在被类型检查）之后，暴露出来的是：

1. `src/components/FileList/*`（4 个文件）—— import 路径写成 `../types`，实际应为 `../../types`。**已废弃代码连类型都编不过**，进一步证明可以直接清掉。
2. `src/components/ImportZone.tsx:20` —— `useDropzone` 的 `accept` 参数类型与 react-dropzone v14 不匹配。
3. `src/components/VirtualFileList.tsx:910` —— `EmptyPlaceholder` 不在 `VirtuosoGrid` 的 `GridComponents` 类型里（运行时靠 props 宽松传递生效，属侥幸）。
4. `src/hooks/__tests__/useExport.test.tsx:87` —— 测试里构造的 `AppFile` 缺 4 个必填字段。

建议：加一个 `"typecheck": "tsc --noEmit"` 脚本并进 CI，再清掉 1 和 4（低风险），2 和 3 随 P1 一起改。
