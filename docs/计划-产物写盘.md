# 计划：产物直接写盘（P3 第二刀）

> 状态：**第 1、2 步已完成**（2026-11-02，含硬链接优化），第 3 步待做（见 TODO「下一步」第 4 条）。
> 目标：把「处理产物」从内存搬到磁盘，让内存占用与批次大小解耦。

## 问题

现在处理完的图全部留在内存（`AppFile.processedBlob`），靠 `processedBlobCache` 的 1.5GB 预算兜底。后果：

1. **批次越大越危险**：1872 张 / 408MB 已经踩过一次 `Out of memory`（打包时 JSZip 再要一份同量级内存）
2. **超预算就丢结果**：LRU 淘汰后标 `evicted`，列表显示「已释放」，**导出时被跳过**——处理了两小时，最后少一批
3. **打包必须先有内存**：无论内置还是本机压缩，产物都得先完整躺在内存里

## 目标

- 处理完立刻落盘，`AppFile` 只记**路径**，内存里不留 Blob
- 导出退化成文件复制（`fs.copyFile`）或直接打包，不经过 JS
- 删掉 `processedBlobCache` / 1.5GB 预算 / `evicted` 全部逻辑

## 三步走（每步可独立验证、可回退）

### 第 1 步：加写盘能力，双存

- 新增 `services/workspace.ts`：会话临时目录 + 清理
- `AppFile` 新增 `processedPath?: string`
- `useProcessing` 处理完把 Blob 写到工作目录，**同时保留 Blob**

**这一步不改变任何现有行为**，只是多存一份路径。验证点：日志能看到写盘路径、磁盘上有文件。

### 第 2 步：导出改走路径

- 目录导出：`fs.copyFile(processedPath, target)` —— 不再读 Blob
- ZIP 打包：优先本机压缩，直接把工作目录里对应文件 `copyFile` 进去
- 内置 JSZip 路径保留（浏览器降级用），但桌面端不再走

验证点：同批次导出速度应明显变快（408MB 从「内存拼包」变成「磁盘复制」）。

### 第 3 步：去掉 Blob 与 LRU

- `processImage` 不再返回 Blob，只返回路径（浏览器环境除外）
- 删 `processedBlobCache`、`MEMORY_SOFT_LIMIT`、`evicted` 相关 UI
- `AppFile.processedBlob` 标为可选，仅浏览器路径使用

## 关键设计

**临时目录**：`~/Library/Caches/com.picman.app/picman-work/<batchId>/`，落在 `fs.scope` 的 `$HOME/**` 内，和现有的 `picman-tmp`（PNG/JPEG 中间件）并列。

**清理策略**（三条，缺一不可）：

| 时机 | 动作 |
|------|------|
| 「清空」列表 | 删整个 batch 目录 |
| 应用启动 | 删超过 24 小时的历史 batch 目录 |
| 处理中断/失败 | 该批次的孤儿文件随下次启动清理 |

**导出后不删**：用户可能同一批导出多次（选目录、再打包），删了就得重处理。

**浏览器降级**：没有 `__TAURI__` 时仍走 Blob，`processedPath` 为 undefined，导出按老路走。这条分支必须保留——它是 `npm run dev` 调试的唯一方式。

## 风险

| 风险 | 对策 |
|------|------|
| 临时文件吃满磁盘 | 启动清 24 小时前的；「清空」即删；文件管理面板可显示占用 |
| 处理中断留孤儿文件 | 按 batch 目录隔离，启动时整目录清 |
| 导出时文件被外部删除 | 导出前 `exists` 检查，缺失的记录到失败清单 |
| `AppFile` 结构变化波及面 | 分三步，每步都跑全量测试 |
