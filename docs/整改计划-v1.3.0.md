# PicMan 整改计划 v1.3.0

> 范围：上一轮使用反馈的 7 项 + 代码评审发现的性能问题
> 基线：`main` @ 9d52dc1（v1.2.2）
> 原则：每一项都必须能独立验证、独立回滚

---

## 一、结论

7 项反馈里有 2 项不是"体验问题"而是**功能失效**：

1. **处理进度条根本不显示** —— 进度相关的三个 state 是重构遗留，从未被置为 `true`。
2. **⌘H 静默失效** —— 自定义菜单把 macOS 标准 App 菜单整组替换掉了，快捷键没有绑定源。

另外 5 项里有 3 项根因明确、改动很小（阴影、选中抖动、通知位置），2 项需要设计决策（体积膨胀策略、日志改版）。

性能部分（详见评审）与体验部分有 2 处交叉，合并做更省事：状态攒批同时解决"列表抖动"和"处理时卡顿"。

## 二、P0 止血（半天，4 项，互相独立）

### 1. 处理进度条不显示

**现象**：点"全部处理"后顶栏没有进度区；按钮一直显示"全部处理"而不是"暂停"；"终止"按钮永远不出现；处理过程中"清空"和"添加文件"仍然可点。

**根因**：`src/App.tsx:41-43` 声明了 `isProcessing` / `isPaused` / `processingProgress`，但全文只有 `setIsProcessing(false)`（第 196 行），**没有任何一处置 `true`**。而顶栏进度区的渲染条件是 `App.tsx:1419` 的 `isProcessing || ...`，所以永远为 false。真正的状态在 hook 里（`hookIsProcessing` / `hookIsPaused` / `hookProcessingProgress`）。

叠加风险：`App.tsx:1598` 的"清空"按钮判断的是 `!isProcessing`，恒为真 → **处理中点清空会清掉正在处理的文件**，状态机错乱。

**改法**：
- 删除这三个遗留 state，全部改读 hook 状态。
- 顶栏进度区保留为"紧凑态"（icon + 百分比 + 暂停/终止）。
- 在文件列表下方新增**完整进度栏**（处理中才出现）：`已完成 137 / 500`、当前文件名、吞吐（张/秒）、剩余时间估算、暂停/继续/终止。这是"处理过程进度条显示"的主要交付物。
- 按钮禁用条件同步改为 `hookIsProcessing`。

**验证**：处理 50 张，进度栏从 0→100% 连续推进；中途暂停后百分比冻结且文案变"已暂停"；终止后进度栏消失、列表里 processing 状态的项回落为待处理；处理中点不到"清空"。

### 2. 顶栏阴影过深

**根因**：`App.tsx:1398` 用了 `shadow-sm/50`。Tailwind v4 把它编译成 `oklab(0% 0 0/.5)`（已在 `dist` 产物中确认），即**50% 纯黑阴影**，比 v4 默认的 10% 深 5 倍。

**改法**：亮色改为 `0 1px 2px rgba(16,24,40,0.04)` 级别的轻阴影，暗色 `dark:shadow-none`（暗色下阴影只会加重边界噪点，靠 1px border 分隔即可）。

**验证**：亮色下顶栏与内容区过渡自然，无灰带；暗色下无阴影层。

### 3. ⌘H 无效

**根因**：`src-tauri/src/main.rs:10-16` 用 `Menu::new().add_submenu(...)` 只放了 close / quit 两个自定义项，把 macOS 默认 App 菜单（About / Services / Hide / Hide Others / Show All）整组替换掉了 → 系统没有可绑定的 Hide 项。

**改法**：补回 Tauri v1 内置原生菜单项（已确认 `tauri-runtime 0.14` 提供）：`MenuItem::Hide`（自动带 ⌘H）、`HideOthers`、`ShowAll`、`Services`；保留自定义 `quit`（需要弹"有未完成的任务"确认框）。Windows / Linux 上用条件编译或 `#[cfg(target_os = "macos")]` 隔离。

**验证**：⌘H 后窗口隐藏、点 Dock 图标能回来；⌘Q 仍弹确认框；⌘W 仍是最小化。

### 4. 体积反而变大时跳过处理

**现状**：`src/hooks/useProcessing.ts:91` 已有防膨胀逻辑，但条件是 `isSizeLarger && !hasEdits`——只要改了格式 / 改了尺寸 / 加了水印，**防膨胀直接失效**。而用户实际遇到"越压越大"的场景，恰恰多是"JPG 转 PNG"这类改了格式的操作。

**改法**：
- `ProcessingConfig` 增加 `sizeInflationPolicy: 'always' | 'skip-if-no-edit' | 'off'`，默认 `'always'`（按本次要求）。
- `AppFile` 增加 `inflation?: { attemptedSize: number; deltaPercent: number }`，跳过时把"处理后会多大"记下来，不丢信息。
- 列表项展示：`原图 1.20 MB → 处理会 1.51 MB (+26%) · 已保留原图`（保留现有 `isSkipped` 徽章，补上被放弃的体积）。
- 日志写一条 `warn`：`跳过（体积膨胀 +26%）：xxx.jpg`。
- 设置面板暴露策略开关，默认严格。

**风险**：用户明确要转成 PNG（无损）时也会被跳过。所以策略必须可切，且列表/日志要说明白"为什么没转"。

**验证**：选一张已高度压缩的 JPEG，输出格式选 PNG → 结果保留原 JPEG，体积与原件一致，UI 显示 `+xx% 已保留原图`；把策略切成 `skip-if-no-edit` → 正常输出 PNG。

## 三、P1 体验（1–2 天，3 项）

### 5. 信息提示条移到底部

**现状**：`App.tsx:1089` 固定在 `top-4`，宽 40vw，翻页式（左右箭头 + 关闭全部），无自动消失。它会挡住顶栏右侧的日志/主题按钮。

**改法**：改 `bottom-4`，宽 50vw，`z-50`；与新增的底部进度栏错开（通知条 `bottom-4`，进度栏在列表内、不浮动）。保留翻页交互（比堆叠更不挡屏幕），左上角加类型图标，行为不变。

**验证**：触发多条提示，底部居中显示、可翻页、点 X 全部关闭；处理中通知与进度栏不重叠。

### 6. 列表缩略图闪动 / 元素抖动

**根因（四条，都在 `VirtualFileList.tsx`）**：
1. 第 229 行：选中态加了 `border-l-4`，未选中没有 → 一选中整行内容右移 4px，肉眼可见抖动。
2. 第 847 / 887 行：`itemContent` 是内联箭头函数，每次渲染新建 → `React.memo` 完全失效；再叠加 `App.tsx` 每完成一张就 `setFiles(prev => prev.map(...))`（第 169 行），整个数组换新 → Virtuoso 每次都全量重算。
3. 行内内容宽度会变：完成时新增 `processingTime` 段、`SizeChange` 从单值变成"原价→现价"，导致行内文字挤压。
4. 第 250 / 397 行：缩略图直接挂原图 blob URL 且 `loading="lazy"`，虚拟列表复用时反复解码大图 → 闪。

**改法**：
- 选中态改常驻 `border-l-4 border-l-transparent`，只换颜色。
- 列表项回调按 id 用 `useCallback` 缓存；`isProcessing` 这个全局 prop 从行内移除（改成在父级禁用交互）。
- 状态更新攒批：`ref` 累积 + 100ms flush 一次（与 P2-③ 是同一处改动）。
- 行内固定槽位：耗时区恒定占位、数字用 `tabular-nums`、行高固定。
- 缩略图：导入时预生成 160–200px 缩略图（复用现成的 `utils/thumbnailGenerator.ts`，目前只在测试里被引用），列表用缩略图；去掉 `loading="lazy"`，加 `decoding="async"` 和固定 `width/height`。

**验证**：1000 文件列表，滚动时缩略图不闪；处理过程中列表不抖、可正常滚动；选中/取消选中时文字不位移。

### 7. 日志改版：完成日志 + 分类 Tab

**现状**：`LogViewer.tsx:20-22` 只有一个 `showAll` 布尔（全量 / 只看 warn+error）；`displayLogs` 每次全量 `reverse`；完成类日志零散，没有耗时和体积汇总。

**改法**：
- 三个 Tab 带条数角标：**正常**（info + success）/ **异常**（warn）/ **错误**（error），默认"正常"。
- 每个操作结束写一条汇总日志，例如：
  `批量处理完成 · 成功 48 · 跳过 3（体积膨胀 2）· 失败 1 · 耗时 12.4s · 总体积 320.5 MB → 210.2 MB（-34%）`
  导入、处理、ZIP、目录导出各一条，字段统一。
- 日志超过 2000 条自动截断更早的记录（防长时间运行内存膨胀）。
- `App.tsx:1504` 的 `logs.some(l => l.level === 'error')` 每次渲染都全量扫，改 `useMemo`。

**验证**：跑一次完整流程，三个 Tab 条数正确、汇总日志字段齐全；连续处理 5 批后日志总量不超过 2000。

## 四、P2 性能（2–3 天，与 P1-⑥ 合并做）

按收益排序，细节见评审：

1. **ZIP 导出改 `compression: 'STORE'`** —— `useExport.ts:151` 现在对已压缩的图片做 DEFLATE，速度慢且基本不省体积。一行改动，导出快 1.5–5 倍。
2. **修 LRU 死代码 + 加内存上限** —— `App.tsx:79` 的 `processedBlobCache` 全文只有 `remove` / `clear`，**从未 `set`**，机制等于不存在；`processedBlob` 全躺在 state 里，1000 张 × 3MB ≈ 3GB。改为按字节预算（建议 512MB）真正写入缓存并淘汰。
3. **状态更新攒批** —— 见 P1-⑥。
4. **调度器去全量排序** —— `taskScheduler.ts:263` 每次 `processQueue()` 都全量 `sort`，而它被每个任务的 `finally` 触发；`getStats()` 又做 6 次全量 `filter`。1000 张会产生上万次冗余排序。
5. **导入去重改 Set** —— `App.tsx:561` 的 `files.some(...)` 在 O(n) 循环里；且 `files` 是导入开始时的快照，并行导入会漏判。
6. **EXIF 改字节拼接** —— `imageProcessor.ts:158-184` 做了三次全文件 base64 转换，5MB 的图每个文件多产生 ~20MB 字符串垃圾。
7. **清理依赖** —— `sharp`（未使用，30MB+ 原生包）、`uuid`（零引用）；`jszip` 改动态 import。

## 五、P3 编码质量（3–5 天，需先定许可）

把 decode → resize → encode → 落盘整条链路搬到 Rust 侧，前端退化为 UI + 缩略图。这一步同时解决主线程卡顿、Blob 内存堆积、Tauri v1 IPC 序列化损耗、编码质量四件事。

- **PNG**：`oxipng`（MIT，Rust，库 API 直接调）。Canvas 导出的 PNG 没做 filter 策略搜索，无损重压通常还能再小 10–30%。
- **JPEG**：`mozjpeg-rs`（纯 Rust，BSD-3，与 C 版字节级一致，免 cmake/nasm）。注意不要用 `jpegli-rs`——算法更新但许可是 AGPL。
- **WebP**：`image-webp`（无损）/ libwebp 绑定（有损）。
- **pngquant（libimagequant）暂缓**：压缩收益最大，但是 **GPL-3.0 / 商业双许可**，与项目 MIT 冲突，需要先定许可方案。
